# P0.3: the puzzle program inside a Firecracker VM

**Date:** 2026-10-26
**Status:** working in GitHub's automated checks ([run](https://github.com/vickey-kapoor/ai-isolation-research/actions/runs/40418699321/job/121907353015)), Firecracker v1.15.0, guest kernel 6.1.155. Also run once on Google Cloud (2026-10-26, see below). Claude's own cloud machine has no KVM, so it can't run this.

## What we built, in plain words

The same puzzle program (an ordinary Python program, not an AI) now runs inside its own small virtual machine. Everything outside (the gate, the checkers, quarantine, approvals, the log) is unchanged from P0.1 and P0.2.

The VM gets exactly three things and nothing more:

| What | Why |
|---|---|
| **Disk 1, read-only:** Python, the puzzle program and the task list | Firecracker can't share folders, so the inputs are baked into a disk when the habitat is sealed. The puzzle program can't change them |
| **Disk 2:** the outbox | A raw disk made of 256-byte slots. On the outside it's the same file the gate reads |
| **1 CPU, 256 MB of memory** | Enough for the puzzle program |

There's no network card, no shared folder, no console and no other device.

Firecracker itself is started by the **jailer**. The jailer puts Firecracker in an empty folder it can't leave, running as the unprivileged user "nobody", with a filter on which system calls it may use. So even the program that pretends to be the VM's hardware has very little it can reach.

**A Windows snag on the way.** The first VM's startup script didn't run: on a Windows checkout with `core.autocrlf=true`, Git gave `startup.sh` Windows line endings, Terraform uploaded it as is, and bash on the VM couldn't execute it. A `.gitattributes` rule now keeps every `*.sh` file LF-only on any checkout.

## Things worth understanding

**Two different walls.** gVisor is a wall made of software: a fake kernel catches the program's requests. Firecracker is a wall made with the CPU's help: the program gets a whole real Linux kernel of its own, and the CPU keeps that VM's memory apart from the host. Both still sit on the host's Linux kernel, but they rely on different parts of it. That's why stacking them (P0.4) is interesting. A failure in one wall doesn't automatically mean a failure in the other.

**Root inside the VM is fine here, in a way it wouldn't be in gVisor.** Inside the VM the puzzle program runs as root, because it is the VM's first and only program. Being root inside a VM only gives power over that VM. The things that matter, the VMM outside and the files it can touch, run as "nobody" in the jail. The wall is the VM, not the user account.

**No shared folders turned out to be a feature.** gVisor needed three bind mounts to give the program its code, its tasks and its outbox. Firecracker can't do that at all, so everything had to go onto disks prepared in advance. That's exactly the PRD's rule that inputs are fixed before sealing (R-O1). The ledger now records the fingerprints of the kernel and the disk image too.

## What this means for the questions

- **Q4 (what each sandbox still trusts):** Firecracker relies on the unverified host kernel (specifically KVM), the CPU's virtualization features, and Firecracker's own code. gVisor relies on the unverified host kernel through a filtered set of system calls, plus gVisor's own code. They're different dependencies, but neither is a verified boundary.
- **Q5 (destroying state):** the kill switch stops the VMM from outside. It doesn't need the VM to cooperate, and the VM gets no warning. The leftover check found nothing: no process, jail folder, disk image, cgroup or mount.

## Gaps, at the PRD level

- **Relies on the unverified host kernel** (KVM) and on the CPU's virtualization being correct. One layer, not a boundary.
- **Some of the VM's hardware is still present but unused.** We turn the guest's serial driver off and connect nothing to Firecracker's output, but the virtual serial port still exists. "Unused" is weaker than "absent".
- **The guest kernel is a download** from the Firecracker project's CI. We record its fingerprint, but we haven't built it ourselves.
- **No resource limits beyond 1 CPU and 256 MB yet.** We haven't looked at how the VM's activity shows up on the host, which matters for PRD R-B2. That's for P0.4.
