# P0.4: gVisor inside a Firecracker VM, and the side-by-side comparison

**Date:** 2026-10-27
**Status:** working in GitHub's automated checks ([run](https://github.com/vickey-kapoor/ai-isolation-research/actions/runs/40439964015/job/121977689734)), on Firecracker v1.15.0, guest kernel 6.1.155 and gVisor release 20261019.0. It hasn't been run on Google Cloud yet. Claude's own cloud machine has no KVM, so it can't run this.

## What we built, in plain words

The same puzzle program (an ordinary Python program, not an AI) now sits behind two walls in a row:

```
host machine (Linux)
└─ Firecracker, in its jail           wall 1: a virtual machine, kept apart by the CPU
   └─ small VM with its own Linux kernel
      └─ gVisor (runsc), no network   wall 2: a kernel written in software
         └─ puzzle program
```

The VM's first program no longer runs the puzzle program itself. It mounts what gVisor needs and then hands over to gVisor. gVisor then starts the puzzle program with the same settings as in P0.2: user "nobody", no capabilities, a read-only root, and the outbox as the only file it can write.

Everything outside (the gate, the checkers, quarantine, approvals and the log) is the same as before.

## The one design change: the outbox

gVisor can only hand the puzzle program ordinary files, not a raw disk. So the VM's second disk now holds a tiny ext2 filesystem containing one file, `outbox.bin`.

- When the habitat is sealed, the outside makes that disk and finds where the file's bytes sit on it. They are one unbroken run of blocks, and the code refuses to continue if they aren't.
- The VM mounts that disk, and gVisor passes the file in.
- The gate outside never mounts or interprets the filesystem. It reads the same fixed byte range it found at sealing, slot by slot, just as it read the raw disk before.

So the outside still doesn't parse anything the inside built: no filesystem structures, only fixed 256-byte frames at a fixed place. The VM's kernel does read the ext2 structures, but that's inside wall 1.

## Things worth understanding

**Stacking costs a bit of start time and a lot of memory, not much else.** Adding gVisor inside the VM added about 0.1 s to the start and about 0.01 s to the kill. The VM needed four times the memory, because gVisor and Python both run inside it. The kill is still a single step from outside: stop the VM. gVisor never gets a say.

**The two walls really are different kinds of thing.** To get through both, a flaw in gVisor's software kernel isn't enough, and neither is a flaw in the VM boundary alone. That's PRD R-B4 (independent layers) in practice. It's still two layers on the same unverified host kernel, so it's defence in depth, not a proof.

**Getting it working taught three small things:**
1. The disk tool on GitHub's machines stored an all-zero file as a "hole" with no disk blocks at all, so there was nothing at a fixed place to read. The fix fills the file with a non-zero value first, then writes the zeros straight into the disk image. A habitat that depends on where bytes physically sit has to check that, not assume it. The sealing code now checks it.
2. gVisor needs a spot to mount the outbox over, and the VM's root disk is read-only, so it couldn't make one. The fix creates it when the disk is sealed. That matches "everything fixed before sealing".
3. To find out why gVisor failed inside the VM, we had to print its own logs to the VM's console. That only happens in the configuration check, which already has a console. The real habitat run still has no console, so no log path leads out. It's a reminder that debugging a sealed box needs a planned way to see in, and that way must not exist in the sealed run.

## What this means for the questions

- **Q2 (does the airlock design survive real sandboxes):** yes, unchanged. The same gate, frames and checkers worked behind one wall, a different wall, and two walls. Only the way the outbox is carried changed, and the gate still reads fixed frames at a fixed place.
- **Q4 (what each layer still trusts):** stacked relies on the host kernel's KVM and the CPU for wall 1. Wall 2 relies on the *VM's* kernel through gVisor's filtered system calls, plus gVisor's own code. The host kernel is still underneath both, and still unverified.
- **Q5 (destroying state):** stopping the VM ends everything inside it, gVisor included, without asking the inside. The leftover check found no process, jail folder, disk image, cgroup or mount.

## Gaps, at the PRD level

- **Everything still relies on the unverified host kernel.** Stacking adds a layer. It doesn't remove that dependency.
- **More code inside the box.** The VM now also carries gVisor and an ext2 filesystem driver in its kernel. Both are inside wall 1, but more code means more that can go wrong, and none of it is verified.
- **The outbox is now a file on a filesystem inside the VM.** The outside ignores the filesystem and reads fixed bytes, but this is one more layer of structure than the raw disk in P0.3.
- **gVisor runs without cgroup limits inside the VM** (`--ignore-cgroups`). The VM's own memory and CPU limits are the real cap. We haven't yet looked at what the VM's activity looks like from the host (PRD R-B2).
