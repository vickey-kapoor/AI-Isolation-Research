# P0.2: the puzzle program inside gVisor

**Date:** 2026-10-26
**Status:** working. Runs on my cloud machine and in CI. gVisor release 20261019.0.

## What we built, in plain words

The puzzle program from P0.1 now runs inside gVisor instead of as an ordinary program. Everything outside (the gate, the checkers, quarantine, approvals, the log) is unchanged. That's the point: the airlock doesn't care what kind of wall is around the puzzle program.

Run it with:

```sh
./sandboxes/setup_gvisor.sh ~/habitat-rootfs            # install runsc, fetch a Python filesystem
sudo python3 -m sandboxes.run_gvisor --rootfs ~/habitat-rootfs
```

What happens, step by step:

1. **Provision and seal.** Same as P0.1: frozen tasks, an empty outbox, three steward keys, the first log entry.
2. **Configuration check.** A tiny probe program starts inside a sandbox with exactly the habitat's settings and answers yes/no questions. The answers we got:

   | Question | Answer |
   |---|---|
   | Network interfaces | only `lo` (loopback, which goes nowhere) |
   | Can it reach the internet? | no |
   | Can it write its own filesystem? | no |
   | Can it change the task list? | no |
   | Can it write the outbox? | yes, and that's the only place |
   | Who does it run as? | user 65534 ("nobody"), no special privileges |

3. **The puzzle program runs** under `runsc`, writing answers in a loop, with no input, no output and no terminal connected.
4. **The gate reads** one slot every 50 milliseconds for 64 ticks. 7 artefacts reached quarantine. The budget held back 5 others until the next period, and 49 rewrites of answers already taken were dropped.
5. **Two stewards release one artefact**, then **two stewards terminate**. The kill switch stops the sandbox, deletes it, and removes every file and mount it left behind.
6. **Leftover check.** No process, no state folder, no outbox and no mount remains.

| Measure | Result on my cloud machine |
|---|---|
| Start time | about 0.09 seconds |
| Kill and destroy time | about 0.02 to 0.03 seconds |

## Things worth understanding

**We drive `runsc` directly, not through Docker.** Docker is a big program with lots of features we don't want. Using `runsc` with a hand-written configuration (`sandboxes/gvisor.py`, function `_spec`) keeps Docker out of the things we have to trust, and puts every setting where you can read it. Docker is used only once, during setup, to download a ready-made Python filesystem.

**gVisor is a "fake kernel".** A program inside asks for things (open a file, make a socket) through system calls. Normally those go straight to the Linux kernel. Under gVisor they go to the Sentry, a kernel written in Go that runs as an ordinary program. The Sentry then uses a small, filtered set of real system calls itself. So the host kernel is still underneath, just with a much smaller door into it. That's why the PRD scorecard will say "relies on the unverified host kernel" for gVisor, though with less of it exposed than a normal container.

**It didn't need KVM.** gVisor's default mode ("systrap") uses ordinary Linux features, not hardware virtualization. That's why it runs on my cloud machine, which has no KVM.

## What surprised us

**"Destroy everything" found something.** The first kill switch run reported a leftover: runsc keeps an empty network namespace pinned as a file (`state/null-netns`). It's how `--network=none` works. It holds no habitat data, but it's a host-side object that outlived the sandbox, and a plain "delete the folder" couldn't remove it. The kill switch now unmounts it first, and the leftover check looks for mounts too. This is a small, concrete example for **Q5**: "destroy all state" needs a definition, a list of what counts as state, and an outside check, not just a delete command.

**The install changed under us.** gVisor's old download link had stopped working. It now ships as a tarball with the Sentry as a separate binary. We pinned a specific release and check its fingerprint, so the build can't change silently again. That's a small taste of the PRD's "inputs frozen before sealing", applied to our own tools.

## Gaps, at the PRD level

- **Relies on the unverified host kernel** (through the Sentry's filtered system calls) and on the Sentry itself being correct. gVisor is one layer, not a boundary.
- **The outbox is a shared file.** The inside can't see reads by design, but that rests on the host filesystem behaving as expected.
- **No resource limits yet.** We haven't capped memory or CPU, so one sandbox could slow its neighbours. That's a PRD R-I6 question ("slower, never a route out") for P0.4.
- **The gate and governance still run as root on the same machine.** Separating them is P0.4.
