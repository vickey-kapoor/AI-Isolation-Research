# P0.1: the airlock core

**Date:** 2026-10-26
**Status:** built, 31 tests passing, demo runs end to end. No sandbox yet.

## What we built, in plain words

Imagine the habitat as a sealed room with a mail slot. This milestone builds everything on the outside of the mail slot, plus a toy resident to post letters through it.

1. **The puzzle program** (`puzzle_program/puzzle_program.py`) reads a task list that was fixed before sealing: five numbers to factorise and two sudoku puzzles. It solves them and writes each answer into its outbox, round and round.
2. **The outbox** (`airlock/outbox.py`) is a file of 256-byte slots. The puzzle program writes. The outside only ever reads. Nothing is ever cleared or marked, so the puzzle program can't tell whether anyone read anything.
3. **The gate** (`airlock/gate.py`) reads one slot per tick, in order, on its own clock. Every frame goes through the checks below.
4. **The frame check** (`airlock/frames.py`): exact size, known header, unused space all zeros.
5. **The verifier** (`airlock/forms.py`): is this an approved form, a task from the frozen list, and the one correct answer, in the one allowed encoding? About 25 lines per form.
6. **The budget** (`airlock/budget.py`): at most N artefacts per period. It can be lowered or closed. There is no code to raise it.
7. **Quarantine** holds what passed. Nothing leaves it without stewards.
8. **Governance** (`airlock/governance.py`): three steward keys, two needed. Four actions only: release, lower the budget, close the airlock, terminate. Each signature covers the exact action and a one-time number (a nonce), so it can't be reused or attached to something else.
9. **The ledger** (`airlock/ledger.py`): a hash chain. Each entry includes the fingerprint of the one before, so editing or removing any old entry is caught.

## Three design choices worth understanding

**One right answer, one way to write it.** Each task has exactly one correct answer, and each answer has exactly one valid byte encoding. For example, factors must be listed smallest first, and `2 × 2` must be written as `2²`. So for a given task, only one frame in the world passes. A passing frame can't carry a hidden message, because there's no choice left in how to write it.

**Rejections leave no trace.** It's tempting to log every rejected frame for debugging. But anything the outside writes down about the inside is information that left the habitat (PRD §8.2). If we logged rejections, the puzzle program could "send" a pattern by choosing which slots to fill with junk. So the ledger records only artefacts that passed every check. Rejections, duplicates and over-budget frames vanish.

**The inside and outside share no code.** The puzzle program writes frames with its own few lines of code, and the gate reads them with separate code. They agree only on the written format. That's the same rule the seL4 plan uses, and it means a bug on one side can't silently match a bug on the other.

## What surprised us (early answers to the six questions)

**Q1: the inside still has some freedom.** Even with unique answers, the puzzle program chooses *which* tasks to answer, *in what order*, and *in which period*. When the budget is full, whichever answers it wrote first get through. In the demo, four of seven answers got through in the first period, and the puzzle program's write order decided which four. That's a small channel, but it's real.

*Opportunity:* instead of accepting first come, first served, the gate could hold verified answers and admit them in an order the outside fixes (for example, lowest task number first). That removes the order freedom, leaving only "answer or don't". The PRD doesn't say this yet. It should.

**Q1, continued: what the outside records is a channel.** The PRD's rule that outside measurements reveal nothing (R-B2) is written about the physical exterior. Phase 0 shows it also needs to apply to the airlock's own logs, counters and error messages. The `stats` counters in the gate exist only so the tests can see what happened; a real gate shouldn't keep them.

**Q2: verifiers can be tiny.** Each form's verifier is about 25 lines, with no dependencies beyond Python itself. That's encouraging. The open part is isolating the verifier *process*, which P0.4 looks at.

**Q3: governance has gaps the PRD doesn't cover.**
- *Same threshold for everything?* Right now closing the airlock needs two signatures, just like a release. The PRD's "fail closed" principle suggests narrowing should be easier than releasing, perhaps one signature. That's the same question as the seL4 plan's open "single-steward emergency stop" decision.
- *Key custody.* How stewards hold their keys, and what happens if one is lost, isn't specified anywhere.
- *Someone has to remember the head.* A hash chain catches edits only if somebody kept an earlier fingerprint to compare against. The PRD should say who holds those copies (for example, each steward keeps the latest head hash).

## What this milestone doesn't do yet

- No sandbox. The puzzle program runs as an ordinary process with full access to the machine. P0.2 (gVisor) and P0.3 (Firecracker) fix that.
- The kill switch is a placeholder that just records it was called. The real one is per sandbox.
- The gate and verifier run in the same process as governance. Separating them is part of P0.4.
